**Date:** 2026-09-10
**Scope:** every source file in `apps/backend`, `apps/frontend`, `packages/*`, `supabase/`, all config, all docs, all 4 worktrees, all uncommitted changes.
**Method:** 8 parallel read-only audit agents, each reading its entire scope top-to-bottom. No files were modified, no builds run, no migrations applied, no remote writes. Secret *values* were never read or printed — only variable names and presence.

## 0. Executive summary

This is a **multi-tenant photo/event SaaS** called FrameFlow. The architecture is sound and the rules in `CLAUDE.md` are genuinely followed: Clerk for auth, Supabase as Postgres only (reached via `pg`, no `supabase-js` anywhere), Appwrite for photo storage only, Express 5 backend, Next.js 16 frontend, no backend logic in Next route handlers, no client-trusted identity.

**The problem is not the architecture — it is that roughly half the product is still demo scaffolding that looks real.**

Three things are simultaneously true:

1. **The admin/team/event/photo backend is real, well-isolated, and tested.** 21 routes, three-layer tenant checks, a genuinely good `uploaded_by`-spoofing test, correct role gates on every mutation.
2. **The customer-facing half does not exist.** The public gallery — the thing the marketing site sells — has *no backend at all*. It runs on a module-level mock array in the browser. A real published gallery renders "Gallery not found."
3. **The upload feature is broken on `main`, and the fix is sitting on an unpushed-into-main branch.** The button that starts the upload is disabled the instant a file is queued, so no request is ever sent. The fix exists as `fix/upload-working` (`d1559e9`), which is pushed to origin but **never merged**.

On top of that: a large amount of demo data (a fake admin named "Alex Kumar", 8,426 photos, 18 team members, three fake notifications, an invented activity feed) is rendered on the first screen a new user sees, with no visual distinction from real data.

## 4. The photo upload pipeline — complete trace

This is the headline of the audit and where the current work has been stuck.

### 4.1 Client side (`upload-modal.tsx`, 306 lines)

**File selection.** Both. `<input type="file" accept="image/jpeg,image/png,image/webp" multiple>` (`:206-216`) and a drag-drop zone (`:177-217`) with `role="button" tabIndex={0}` and Enter/Space handling (`:196-201`) — genuinely accessible. **No auto-start on drop.**

**Validation.** MIME allowlist `["image/jpeg","image/png","image/webp"]` (`:67`); per-file 25 MB (`:69`, `MAX_FILE_BYTES` at `:29`); aggregate rejection toast listing the first 3 names (`:75-80`). **Missing:** no file-count cap client-side (backend caps at 20), no zero-byte check, no total-bytes cap, no dedup.

**The bug.** `upload-modal.tsx:98`:

```ts
const uploading = items.some((i) => i.status === "uploading" || i.status === "queued");
```

`:285`:
```tsx
<Button disabled={uploading || items.length === 0 || phase === "uploading"} onClick={startUpload}>
```

Adding files sets every item to `"queued"` (`:45`) → `uploading` becomes `true` → the button is **disabled** and its label reads "Uploading…". `startUpload()` has exactly one caller (`:286`) and there is no auto-start. **No user action can send a request.** This is precisely the "spins forever at 0%" symptom with "ZERO requests arrived" in the backend log.

**The fix** (branch `fix/upload-working`, commit `d1559e9`):
```ts
const uploading = items.some((i) => i.status === "uploading");
const pendingCount = items.filter((i) => i.status === "queued" || i.status === "failed").length;
// ...
disabled={uploading || pendingCount === 0}
onClick={() => void startUpload()}
```
It also fixes `retry()`, which read the stale `items` array right after `setItems`, and adds browser-verified evidence in the commit message. **Not on `main`.**

**A second, independent bug** (branch `fix/upload-auth-session-recovery`): `:122` is a bare, unbounded `await getToken()`. If Clerk's promise stays pending, the modal hangs at 0% with no cancel. That branch adds `getSessionToken()` — 15s `Promise.race` + one retry with `skipCache` + `isLoaded`/`isSignedIn` guards. **Also not on `main`.**

The uncommitted work on `main` adds only a null-token guard (`:124-126`, a genuine small improvement) and five `console.log` statements — **it does not fix either bug.** `SESSION_HANDOFF.md` §8 blames "stale cookies / infinite redirect loop"; that diagnosis is **wrong** — the branch evidence is decisive.

**The request.** One single multipart POST for the entire batch:

```
POST {NEXT_PUBLIC_API_URL}/api/v1/events/{eventId}/photos
Authorization: Bearer <Clerk session JWT>   // only if token truthy
Content-Type: multipart/form-data           // browser-set
Body: FormData with N × part name="photos"
```
`client.ts:143-169`. Field name `photos` matches `upload.array("photos", 20)` (`upload.ts:25`). `xhr.timeout = 120_000` (`client.ts:147`, added uncommitted, works). **Concurrency: 1 — there is no per-file request, no worker pool, no batching.**

**Progress.** Real, via `xhr.upload.onprogress` (`client.ts:149-153`) — but it is **one aggregate percentage for the whole batch**, applied identically to every row (`upload-modal.tsx:131-134`). All N bars move in lockstep. It also reaches 100% *before* Appwrite + Postgres finish, so rows sit at "100%" for seconds. Each tick fires a `console.log` (`:129`).

**Failure handling.** One `try`/`catch` for the whole batch (`:120-156`). No per-file attribution. Backend returns **502 with `{error, uploaded[]}`** (`api.ts:441-448`) listing the files that *did* persist — and `uploadPhotos` (`client.ts:157-162`) **discards `uploaded`**, rejects, and the modal marks **every** item failed (`:151-154`). Retry then re-uploads the successes → **silent duplicates in both Appwrite and Postgres.** There is no idempotency key.

**Cancellation.** **None.** No `AbortController`, no `xhr.abort()`. "Cancel" (`:281-283`) just closes the dialog; the close effect (`:84-96`) wipes the queue and revokes preview URLs while the XHR keeps running, then the promise resolves and calls `onUploaded()` — which on the event page is `window.location.reload()` (`events/[eventId]/page.tsx:347`), killing the request mid-flight.

**Duplicate IDs.** `id: \`upload-${i}-${file.name}-${file.size}\`` (`:41`) — `i` restarts at 0 per `addFiles` call, so the same file added in two separate picks produces **two items with the same id**, colliding React keys and making every `ids.includes(it.id)` update hit both.

**Image processing.** **None.** No thumbnails, no derivatives, no resize, no EXIF strip/read/orientation, no HEIC, no RAW, no magic-byte sniffing. The grid loads full-resolution originals for every tile.

### 4.2 Server side (`api.ts:388-453`, `upload.ts`, `storage.ts`)

Middleware order: `helmet → cors → compression → express.json({limit:"1mb"}) → requireAuth → photoUpload (multer) → multerErrorHandler → handler`. **Correct** — auth runs before any body buffering.

1. **Multer** (`upload.ts`): `memoryStorage()` — the whole batch is buffered in the Node heap. `limits: {fileSize: 25MB, files: 20}`, `fileFilter` rejects non-allowlisted MIME via `HttpError(400)`. **20 × 25 MB = up to 500 MB heap per request**, with no rate limiting anywhere → memory-exhaustion vector from one authenticated account.
2. **Authz** (`authorizeEventAccess`, `api.ts:374-386`): `resolveAppUser` → `getWorkspaceEvent(eventId, user.workspace_id)` → 404 if not in workspace, 403 if member not assigned.
3. **Per-file loop, sequential.** MIME re-check → `uploadPhoto` (Appwrite `createFile`, key = `randomUUID()`, **no `permissions` argument**) → `insertPhoto` (Postgres, `event_id` from the DB row, `uploaded_by` from the verified identity).
4. **Ordering: storage first, DB second.** Inner `catch` cleans up the Appwrite object if the metadata insert fails (`:436-440`). **No cleanup** if the process dies between the two.
5. **Not transactional.** Two external systems, no saga, no compensating transaction, no idempotency key.

**Notable defects:**
- The per-file MIME re-check (`:413-416`) returns a bare 400 with **no `uploaded` array** — strictly worse than the 502 branch, since earlier files are already committed and the client learns nothing.
- `DELETE /events/:id` cascades DB rows (photos, galleries) but **never deletes the Appwrite binaries** → every photo of a deleted event is orphaned forever. There is no sweeper or reconciliation job.
- **No thumbnail generation anywhere.** No `thumb` hits in the backend, no thumbnail column, and Appwrite's `transformations: true` is enabled but never used to build a preview URL.

### 5.2 Auth model

`requireAuth` (`auth.ts:39-79`):
1. Requires the literal `"Bearer "` prefix (case-sensitive) → else `401`
2. `verifyToken(token, {secretKey})` — networkless JWT verification → else `401`
3. `payload.sub` = Clerk user id
4. **A live Clerk API call `users.getUser(sub)` on every single request** to fetch name/email/metadata — ~100–300ms of third-party latency per call, no timeout, no cache, no circuit breaker
5. On failure, `catch {}` leaves `name: ""`, `email: ""` — and `upsertUserFromClerk` then **persists those empty strings over good data** (`db.ts:187-191`). `email` is the key used for invitation matching, so a transient Clerk outage can break provisioning.

`requireRole` (`auth.ts:85-107`): reads `SELECT role FROM users` — a DB round-trip per gated request, no cache. **Runs before `resolveAppUser`**, so a brand-new invited user hitting any admin route gets a `403` until they happen to call `/me` or `GET /events` (which auto-provision).

**Identity is exclusively `payload.sub`.** No route reads `workspace_id`, `user_id`, or any identity from the body/query/params. Zod strips unknown keys, so `workspace_id` cannot be smuggled through a validated body. The `assignEventMember` body carries `{user_id}` but the backend re-validates the target against the actor's workspace — a *target selection*, not an identity claim. **This is the strongest part of the design.**

`verifyToken` is called **without `authorizedParties`** — the token is not pinned to this frontend origin.

**The one cross-tenant hole:** `upsertUserFromClerk` (`db.ts:140-147`) resolves the workspace from `getPendingInvitationByEmail` (`db.ts:427-436`), which filters **by email only**, orders `created_at DESC`, and returns `.rows[0]` — with **no `UNIQUE` constraint on `invitations.email`** (only a plain index, migration 3). An admin of workspace B who invites an address already invited to workspace A *later* wins; the invitee is attached to B. ## 7. Data model

8 tables across 5 migrations. No `DROP` and no `ALTER TYPE` anywhere — genuinely clean on the most dangerous category.

### Final schema (consolidated)

**`users`** — `id` uuid PK, `clerk_user_id` text UNIQUE, `name`/`email` text, `role` enum `user_role` default `TEAM_MEMBER`, `workspace_id` uuid NOT NULL → `workspaces(id)` `NO ACTION`, timestamps, `updated_at` trigger.

**`workspaces`** — `id` PK, `name` text (no unique), `created_by` → `users(id)` `NO ACTION`, timestamps. **No indexes.**

**`events`** — `id` PK, `name`/`description`/`location`, `event_date` **SQL `date`**, `status` text CHECK `('draft','active','completed')` (unnamed constraint), `created_by` → `users(id)` **`ON DELETE CASCADE`**, `workspace_id` NOT NULL, timestamps.

**`event_team_members`** — composite PK `(event_id, user_id)`, `added_by` → `users` `SET NULL`, `added_at`. **No `workspace_id`** — see below.

**`photos`** — `id` PK, `event_id` → `events` CASCADE, `uploaded_by` → `users` **`NO ACTION`**, `filename`, `storage_file_id` text with a **global `UNIQUE`**, `storage_provider` text default `'appwrite'` (**no CHECK**), `mime_type` (no CHECK), `file_size` **`integer`** (~2.1 GB ceiling), timestamps.

**`galleries`** — `id` PK, `event_id` → `events` CASCADE, `name`, `description`, `slug` text **`UNIQUE` (global)**, `pin` text (**no format CHECK**, plaintext), `status` text CHECK `('draft','published')`, `published_at` nullable with **no invariant tying it to status**, `created_by` → `users` **`NO ACTION`**, timestamps.

**`gallery_photos`** — composite PK `(gallery_id, photo_id)`, both CASCADE, `added_at`.

**`invitations`** — `id` PK, `email` (**no UNIQUE**), `workspace_id` → `workspaces` CASCADE, `invited_by` → `users` **`NO ACTION`**, `status` enum `invitation_status`, `clerk_invitation_id` nullable, timestamps.

### Tenancy

Tenant = a `workspaces` row. `users.clerk_user_id` is the only Clerk reference in the schema — **Clerk Organizations are not modelled at all.** A user belongs to exactly one workspace, forever; there is no join table and no route can change it.

Tables carrying a tenant column: `users`, `events`, `invitations`. `photos` and `galleries` resolve through `event_id`. `gallery_photos` is a pure join.

**`event_team_members` has no tenant column and no constraint tying `event_id` and `user_id` to the same workspace.** A cross-workspace row is structurally representable; only `api.ts:519-524` prevents it. The defence holds today (the routes gate on `getWorkspaceEvent` first), but any future direct call to `addEventMember` bypasses it with no DB backstop.

### Delete cascade chain — a real hazard

`DELETE /team-members/:id` does a bare `DELETE FROM users`. Three FKs are `NO ACTION`:
- `photos.uploaded_by` → **blocked** for any user who ever uploaded
- `galleries.created_by` → **blocked** for any user who created a gallery
- `invitations.invited_by` → **blocked** for anyone who ever invited, which is *every* admin

So the route returns an undocumented **500** instead of a clean 4xx for a demoted admin (an admin who invited people, was later demoted to TEAM_MEMBER, and is now removable). The admin block fires first so it's masked in the common case — but the failure mode is real.

Deleting a **workspace** is impossible: `users.workspace_id` and `events.workspace_id` are `NO ACTION` and every user has a workspace. The tenant is effectively immortal.

### RLS

**Enabled on all 8 tables with ZERO policies, zero GRANTs, zero views, zero `SECURITY DEFINER` functions.** The migration comment claims direct client access "is denied" — and it is, because `ENABLE` + no policy is deny-by-default for `anon`/`authenticated`. The posture is nonetheless **implicit**: there is no `REVOKE`, no `FORCE ROW LEVEL SECURITY`, and a single future `CREATE POLICY ... USING (true)` silently opens a table. **Isolation depends entirely on backend `WHERE` clauses** — there is no second line of defence.

### Migration hygiene

- **No migration is idempotent** (all bare `CREATE`; only `create or replace function` is repeatable). Normal for Supabase, but the backfill DML in migration 3 is not idempotent either.
- **No down-migrations at all.** Migration 3 is one-way: after `SET NOT NULL` there is no restore path.
- **Migration 3 has a latent correctness bug.** The workspace backfill **excludes** admins who have any `event_team_members` row (`:31`), while the later assignment step only matches `w.created_by = u.id` (`:68`) — mutually exclusive. It worked on the live DB, which means no admin had an event assignment at migration time. On any DB where an admin *was* assigned to an event (a perfectly normal state — `POST /events/:id/team-members` accepts admins), **migration 3 fails and the deploy is blocked** with an error pointing at the wrong line.
- **The live DB's migration versions do not match the repo filenames** (`20260907203435` vs `20260908000000`, etc.) — the schema was applied through a rewritten history. Repo and live schema are out of sync.
- `pgcrypto` is never created, though every table depends on `gen_random_uuid()`.
